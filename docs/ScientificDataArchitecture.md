# IUVFES Scientific Data Architecture

## Objective

IUVFES is being designed so that laboratory experiments, Digital Twin simulations, analyses and scientific reports remain connected through durable provenance. The goal is not merely to store results, but to preserve how every result was produced and how the model evolves when new evidence arrives.

## Source-of-truth hierarchy

```text
REAL LABORATORY
     |
     v
RAW OBSERVATIONS  <--- immutable source evidence
     |
     +--> PROCESSED DATA
     |
     +--> DIGITAL TWIN SIMULATION
     |         |
     |         +--> prediction error
     |         +--> model version
     |
     +--> ANALYSIS
               |
               +--> FINDING
               +--> HYPOTHESIS
               +--> SCIENTIFIC REPORT / JOURNAL
```

Simulation must never silently overwrite experimental evidence. AI analysis must never rewrite raw measurements.

## Required identity chain

Every research run should be traceable through:

```text
Experiment ID
  -> Sample ID
  -> Material ID
  -> Instrument IDs
  -> Calibration IDs
  -> Researcher IDs
  -> Protocol version
  -> Raw dataset ID/version
  -> Processed dataset ID/version
  -> Simulation/model version
  -> Analysis version
  -> Findings
  -> Journal/report
```

The contracts in `shared/scientificData.ts` define the first version of these objects.

## Provenance

`server/scientificProvenance.ts` provides an in-process provenance journal and deterministic SHA-256 dataset hashing. Each provenance event records an entity, activity, agent, time, inputs and outputs. The journal is deliberately isolated from raw scientific data: persistence should be added to the research-data store without changing the meaning of the raw dataset.

## Data quality lifecycle

```text
RAW
  -> VALIDATED
  -> REVIEWED
  -> CALIBRATED
  -> REPLICATED
  -> PUBLISHED
```

Exceptional states:

- `RETRACTED` — published/released data must no longer be treated as valid evidence.
- `SUPERSEDED` — a newer version replaces the dataset for normal use, while the previous version remains traceable.

No lifecycle transition should delete the previous version.

## Real experiment vs simulation

Both are first-class sources, but they must remain distinguishable:

- `EXPERIMENTAL`: measured by a physical laboratory setup.
- `SIMULATION`: generated by a model.
- `DERIVED`: calculated from existing datasets.
- `AI_ANALYSIS`: interpretation or inference generated by an analysis system.

A simulation result should reference the experimental data used for calibration/validation and retain the exact model/software version.

## Dataset integrity

Each releasable dataset should have:

- stable dataset identifier;
- semantic version;
- creation timestamp;
- creator/researcher identity;
- instrument and calibration references;
- software and model version;
- provenance references;
- SHA-256 checksum;
- quality status;
- license/access policy;
- DOI when published.

## Scientific notebook

A future experiment UI should capture objective, hypothesis, material/sample, procedure, environmental conditions, parameters, raw telemetry, operator observations, anomalies, attachments, analysis and conclusion as one traceable experiment record.

## Journal generation

A report generator should construct a reproducible manuscript from linked records rather than copying numbers into prose. At minimum:

1. Title
2. Abstract
3. Keywords
4. Introduction
5. Materials and Methods
6. Experimental Configuration
7. Instrumentation and Calibration
8. Results
9. Statistical Analysis
10. Mass/Energy Balance
11. Digital Twin Comparison
12. Discussion
13. Limitations
14. Conclusion
15. References
16. Dataset and supplementary-data manifest
17. Software/model versions

AI-generated interpretation must be explicitly labeled as interpretation or hypothesis until supported by evidence.

## Long-term architecture

The Git repository should contain source code, schemas, model definitions, analysis pipelines and documentation. Large raw datasets, sensor streams, images and video should live in a research-data/object store. Git should retain stable dataset IDs, manifests, checksums and release metadata so software and data remain reproducible without putting large experimental streams into source control.

## Reproducibility rule

A published result should be reconstructable from:

`experiment + raw dataset version + calibration + analysis version + software commit + model version + configuration`.

If any required component is missing, the result should be marked as not fully reproducible rather than silently reconstructed.

## Scientific integrity rule

IUVFES must preserve failed experiments, anomalies and negative results. A failed run is evidence, not garbage. Corrections create a new derived version with an explanation and never erase the original observation.

This architecture is a research-data foundation, not a claim that current simulator parameters are experimentally validated. Calibration and validation against real laboratory measurements remain mandatory.
